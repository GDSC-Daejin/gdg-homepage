# 기능 추가 · 개선안 제안

> 2026-07 기준, 현재 구현된 서비스를 기반으로 PM · 디자이너 · 엔지니어 세 관점에서 아이디어를 펼치고 상위 5개를 선정했다.

## 현재 서비스 요약

| 영역 | 구현된 것 |
|---|---|
| 공개 | 지원서(모집 기간 제어, 익명 지원), 소개/팀/프로젝트, 이벤트 목록 |
| 회원 | 온보딩, 프로필(월간 포인트·배지·영어 닉네임), 이벤트 신청(정원·대기열), 출석 체크인(event_code), 공지, 설문(프리셋), 문의, 자료실, 자유게시판·Q&A(채택 답변) |

## 1. PM 관점 — 비즈니스 가치 · 전략 정합성

1. **출석 자동 포인트 적립** — 체크인 성공 시 포인트를 자동 지급. 현재 포인트는 어드민 수동 지급뿐이라 운영 부담이 크고 적립 빈도가 낮다. 출석→보상 루프가 생기면 이벤트 참여 자체가 리텐션 엔진이 된다.
2. **합격자 온보딩 퍼널 완성** — 합격 메일에 온보딩 딥링크를 넣고, 온보딩 미완료 회원을 어드민에서 추적. 승격(accepted→member)은 자동인데 그다음 단계가 끊겨 있다.
3. **이벤트 리마인더** — 이벤트 전날/당일 신청자에게 Slack 알림. 기존 cron·Slack 인프라 그대로 재사용. 노쇼 감소 = 출석 경고 cron의 예방 버전.
4. **활동 리포트(기수/학기 단위)** — 출석률·포인트·게시판 활동을 모아 회원별/전체 요약. 어드민의 수료·우수회원 선정 근거이자 회원의 "내 활동" 동기부여.
5. **모집 대시보드** — 모집 기간 중 지원서 유입 추이, 심사 상태 분포를 어드민 홈에서 한눈에. 현재는 지원서 목록만 있어 흐름 파악이 어렵다.

## 2. 디자이너 관점 — 경험 · 사용성

1. **회원 홈 대시보드** — 로그인 직후 다가오는 이벤트·미응답 설문·새 공지·이번 달 포인트를 카드로 요약. 현재는 회원이 메뉴를 돌아다니며 직접 확인해야 한다.
2. **이벤트 캘린더 뷰** — 목록 외에 월간 캘린더 토글. session/study/devfest/mogakco 타입별 색상 구분.
3. **인앱 알림 센터** — 문의 답변 완료, 정원 대기→확정 승급, 배지 수여를 헤더 벨 아이콘으로. 지금은 회원이 결과를 알 방법이 재방문뿐이다.
4. **멤버 디렉토리** — 닉네임·포지션·배지를 보여주는 회원 목록. 커뮤니티인데 서로를 볼 수 있는 화면이 없다. 공개 범위는 프로필에서 본인이 제어.
5. **게시판 작성 경험 개선** — 마크다운 미리보기·이미지 첨부. `Markdown.tsx` 렌더러가 이미 있으니 작성 쪽만 붙이면 된다.

## 3. 엔지니어 관점 — 기술 가능성 · 보유 데이터 활용

1. **정원 승급 자동 알림** — `cancelRegistration`의 대기열 승급 시점에 승급자에게 Slack/알림 발송. 승급 로직·webhook 모두 이미 있고 훅 한 줄 거리다.
2. **통합 검색** — 공지·게시판·자료를 Postgres FTS(tsvector)로 검색. 외부 검색엔진 불필요, 마이그레이션 하나로 해결.
3. **출석 QR 코드** — `IssueCodeButton`이 발급하는 event_code를 QR로도 렌더링. 현장에서 코드 구두 전달 대신 화면 스캔.
4. **Community Store 마이그레이션 완주** — `docs/design/community-store-design.md` 설계대로 남은 액션들을 store 경유로 전환. Demo Mode 신뢰성과 테스트 용이성이 함께 올라간다.
5. **포인트 지급 규칙 테이블** — `admin_grant_points` RPC 앞단에 규칙(출석 N점, 설문 응답 N점)을 두고 자동 지급 이벤트가 참조. 수동 지급과 감사 로그 체계는 그대로 유지.

## ⭐ 상위 5개 선정

평가 기준: 전략 정합성(커뮤니티 리텐션) · 임팩트 · 공수 · 기존 인프라 재사용도.

### 1. 출석 자동 포인트 적립
- **한 문장**: 출석 체크인 성공 시 정해진 포인트를 자동 지급한다.
- **선정 이유**: 포인트·배지·출석 시스템이 전부 이미 있는데 서로 연결만 안 돼 있다. 액션 하나에 RPC 호출을 추가하는 수준의 공수로 참여 보상 루프가 완성된다.
- **핵심 가정**: "포인트가 실제로 참여 동기가 된다."
- **확인 방법(사람 없이)**: `point_logs`와 `attendances`를 조인해 과거 수동 포인트 지급 후 해당 회원의 다음 이벤트 출석률 변화를 분석. 변화가 없으면 포인트는 기록용으로만 유지.

### 2. 이벤트 리마인더 + 정원 승급 알림
- **한 문장**: 이벤트 전날 신청자에게, 대기→확정 승급 시 승급자에게 Slack 알림을 보낸다.
- **선정 이유**: 출석 경고 cron·`postSlack`이 이미 있어 재사용률이 가장 높다. 노쇼와 "승급된 줄 몰라서 못 온" 케이스를 동시에 줄인다.
- **핵심 가정**: "노쇼의 주 원인이 잊어버림이다."
- **확인 방법**: `event_registrations`(confirmed)와 `attendances`를 대조해 노쇼율과 신청~이벤트 사이 간격의 상관을 분석. 간격이 길수록 노쇼가 높으면 리마인더 효과 가능성이 크다.

### 3. 회원 홈 대시보드
- **한 문장**: 로그인 직후 다가오는 이벤트·미응답 설문·새 공지·이번 달 포인트를 한 화면에 요약한다.
- **선정 이유**: 새 데이터가 전혀 필요 없다 — 이미 있는 read를 한 페이지에 모으는 조합 작업. 모든 회원이 매 방문마다 지나는 화면이라 노출 임팩트가 가장 크다.
- **핵심 가정**: "회원이 설문·공지를 놓치는 이유가 발견성 부족이다."
- **확인 방법**: 설문 응답 시각 분포 분석 — 응답이 공지 발행 직후에만 몰려 있고 롱테일이 없다면, 재방문 시 발견 실패가 맞다.

### 4. 통합 검색 (공지 · 게시판 · 자료)
- **한 문장**: Postgres FTS로 공지·게시글·자료를 한 검색창에서 찾는다.
- **선정 이유**: 콘텐츠(공지·게시판·자료실)가 쌓이기 시작한 시점이라 지금 넣는 게 가장 싸다. 마이그레이션 1개 + 검색 페이지 1개로 끝난다.
- **핵심 가정**: "찾고 싶은 과거 콘텐츠가 실제로 존재할 만큼 쌓였다."
- **확인 방법**: posts·notices·materials 행 수와 월별 증가 추이 조회. 총량이 수십 건 미만이면 검색 대신 목록 필터로 충분 — 보류.

### 5. 인앱 알림 센터
- **한 문장**: 문의 답변·정원 승급·배지 수여를 헤더 벨 아이콘의 알림 목록으로 보여준다.
- **선정 이유**: 서비스의 여러 비동기 이벤트(답변·승급·수여)가 전부 "회원이 다시 와서 확인"에 의존하고 있다. `notifications` 테이블 하나로 2번(승급 알림)의 인앱 버전까지 흡수하는 공통 기반이 된다.
- **핵심 가정**: "알림 받을 사건이 회원당 유의미한 빈도로 발생한다."
- **확인 방법**: 최근 3개월 inquiries 답변 수·waitlist 승급 수·배지 수여 수를 회원 수로 나눠 월간 발생 빈도 산출. 월 1건 미만이면 Slack 알림(2번)만으로 충분 — 보류.

## 우선 실행 제안

1→2→3 순서를 추천. 1·2는 기존 인프라 조립이라 각각 소규모 PR로 끝나고, 3은 그 결과(포인트·알림)를 보여줄 무대가 된다. 4·5는 데이터 확인(위 가정 검증 쿼리) 후 착수 여부 결정.
