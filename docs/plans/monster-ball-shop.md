# 꼬북봇 포인트 몬스터볼 상점 구현 계획

> 상태: Ready

## 1. 현재 코드 기준

- 꼬북봇 물 마시기 인증과 시즌 보너스는 기존 `point_logs`에 포인트를 적립한다.
- 트레이너 마켓봇은 별도 `trainer_point_logs`를 사용한다.
- 트레이너 마켓봇에는 이미 Slack `/포켓몬 상점`이 있다. 몬스터볼 1~3개를 개당 200TP로 즉시 교환하고, `trainer_buy_balls` RPC가 TP 차감과 `pokemon_ball_inventory` 지급을 한 트랜잭션으로 처리한다.
- 일일 무료 보충은 현재 보유량이 3개보다 적을 때만 3개까지 채우므로, 구매한 볼은 보존된다.
- 일반 서비스 포인트용 웹 상점 설계(`store_items`, `point_redemptions`)는 문서만 있고 현재 마이그레이션 구현은 없다.

## 2. 이번 기능의 기회

꼬북봇 활동으로 쌓인 포인트를 실제 포획 기회로 바꿔 포인트의 사용처를 만든다. 목표는 상점을 크게 만드는 것이 아니라, 포인트 확인 → 몬스터볼 교환 → 도감 포획으로 이어지는 짧은 루프를 완성하는 것이다.

### 먼저 결정할 것

| 선택지 | 의미 | 판단 |
| --- | --- | --- |
| 기존 `trainer_point_logs` 사용 | 현재 Slack 상점의 TP 경제와 동일한 화폐를 사이트에서도 사용 | 기존 게임 경제를 유지할 때 |
| 기존 `point_logs` 사용 | 꼬북봇 인증 포인트를 사이트 상점에서 직접 사용 | 이번 요청의 “꼬북봇 포인트”에 가장 가까움 |
| 두 포인트 연결 | 한쪽 포인트를 다른 쪽으로 환전하거나 합산 | 초기에는 복잡도와 경제 누수 때문에 제외 |

이 문서는 두 번째, 즉 **꼬북봇이 적립한 기존 `point_logs`를 사이트에서 몬스터볼로 교환**하는 안을 기본안으로 작성한다. 단, `point_logs`는 출석·관리자 지급 포인트도 함께 담으므로 “꼬북봇 전용 포인트”가 꼭 필요하면 별도 원장을 먼저 결정해야 한다.

## 3. MVP 제안

운영 가격·구매 제한·진화 기여도 보상은 [프렌들리숍 몬스터볼 운영 정책](../policy/monster-ball-shop.md)을 기준으로 구현한다.

### 회원 흐름

1. 회원이 사이트 `/store`에서 사용 가능 포인트와 몬스터볼 보유량을 확인한다.
2. `몬스터볼 1개 교환`을 누른다.
3. 확인 화면에 차감 포인트, 교환 후 잔액, 교환 후 보유량을 보여 준다.
4. 확인 순간 포인트 차감과 볼 지급을 원자적으로 처리한다.
5. 상점 또는 프로필에서 교환 이력을 확인한다.

### 기본 상품

상품 구성과 운영 규칙은 정책 문서에서 관리한다. 구현에서는 1개·3개·5개 상품과 정책에 정의된 일일 한도를 제공한다.

## 4. 역할별 아이디어

### PM 관점

1. **기본 교환 상점** — 포인트를 몬스터볼로 바꾸는 핵심 루프만 먼저 제공한다.
2. **교환량 파일럿 측정** — 가격을 고정한 뒤 2주간 사용자별 교환률·중앙 교환량을 확인한다.
3. **활동 연결 문구** — 포인트가 부족할 때 꼬북봇 인증 방법을 바로 안내한다.
4. **시즌 보상 연계** — 시즌 종료 보너스가 추가 포획으로 이어지는지 확인한다.
5. **이벤트 보너스 볼** — 특별 이벤트 때만 추가 교환 기회를 제공한다.

### 디자인 관점

1. **상점 카드 1개** — 이미지, 가격, 현재 보유량, 교환 버튼을 한 카드에 둔다.
2. **교환 확인 모달** — 차감 전·후 잔액과 볼 수량을 한눈에 보여 준다.
3. **부족 상태 안내** — 버튼을 막는 대신 필요한 포인트와 획득 경로를 표시한다.
4. **상점과 도감 연결** — 교환 완료 후 도감으로 이동할 수 있게 한다.
5. **최근 교환 내역** — 회원이 포인트가 왜 줄었는지 바로 확인할 수 있게 한다.

### 엔지니어링 관점

1. **원자적 교환 RPC** — 포인트 차감과 인벤토리 증가가 함께 성공하거나 함께 실패한다.
2. **교환 원장** — 모든 교환을 별도 기록해 중복 지급과 고객 문의를 추적한다.
3. **재시도 멱등성** — 요청 ID를 받아 더블클릭·네트워크 재시도에서 중복 차감·지급을 막는다.
4. **잔액 재검증** — 화면에 표시된 잔액을 믿지 않고 RPC 안에서 다시 계산한다.
5. **기존 인벤토리 재사용** — `pokemon_ball_inventory`와 기존 일일 보충 로직을 수정 없이 연결한다.

## 5. 우선순위

| 순위 | 결정 | 이유 | 검증할 가정 |
| ---: | --- | --- | --- |
| 1 | 기존 포인트 → 몬스터볼 원자적 교환 | 기능의 본질이며 가장 작은 범위 | 포인트 사용처가 참여 동기를 높이는가 |
| 2 | 정책 문서 기준 상품·일일 제한·즉시 지급 | 운영 규칙과 구현 계획을 분리하면서 대량 구매를 막는다 | 일일 제한이 포인트 소비와 참여를 균형 있게 만드는가 |
| 3 | 확인 모달 + 교환 결과 | 실수 구매와 문의를 줄인다 | 구매 전후 정보를 충분히 이해하는가 |
| 4 | 교환 원장과 회원 이력 | 포인트·인벤토리 불일치 원인을 추적한다 | 운영자가 이력만으로 문제를 확인할 수 있는가 |
| 5 | 2주 가격 파일럿 | 경제 수치를 추측하지 않고 실제 사용량으로 조정한다 | 사용자별 주간 교환량이 목표 범위에 들어오는가 |

## 6. 구현 시 지켜야 할 규칙

- 포인트 잔액은 기존 원장의 합계로 계산하고 별도 잔액 컬럼을 만들지 않는다.
- 구매 기록, 음수 포인트 로그, 인벤토리 증가는 한 DB 트랜잭션에서 처리한다.
- 회원 화면의 버튼 비활성화는 편의 기능일 뿐이며, 최종 검증은 RPC에서 한다.
- 일일 구매 제한과 진화 기여도 보상은 [운영 정책](../policy/monster-ball-shop.md)대로 RPC에서 검증한다.
- 무료 일일 보충은 `greatest(현재 보유량, 3)` 정책을 유지한다.
- 물리 상품 상점의 승인·배송·예산 연동·재고 모델은 몬스터볼에 추가하지 않는다.
- 고급 볼·쿠폰·선물·환전·회원 간 송금은 파일럿 지표가 필요성을 보여 줄 때까지 만들지 않는다.

## 7. 구현 범위에서 제외

- 교환 이력 운영진 화면은 후속으로 둔다.
