# DB 함수의 정본은 마이그레이션 파일 그 자체다

마이그레이션 85개 안에 함수 정의가 120번 등장하지만 고유 함수는 75개다. 함수를 고칠 때마다 `create or replace` 전문을 다음 번호 파일에 다시 붙여넣기 때문이다(`handle_new_user` 6벌, `pokedex_throw_ball` 4벌, `pokedex_rank_state` 4벌). 함수 본문을 `supabase/functions/`에 한 벌만 두고 마이그레이션을 생성하는 방식이 자연스러워 보이지만, **채택하지 않는다.**

**결정**: 함수 정본을 따로 두지 않는다. 마이그레이션 파일이 곧 정본이고, 살아있는 정의는 "그 함수를 정의한 파일 중 번호가 가장 큰 것"이다. 사본이 쌓이는 비용은 감수한다.

## Considered Options

- **`supabase/functions/`에 정본 파일 + 마이그레이션 생성 스크립트**: 편집이 한 곳으로 모이고 diff가 규칙 변경만 보여준다. 그러나 (1) 마이그레이션은 append-only다 — `supabase db push`가 원격 `schema_migrations`에 파일명을 기록하므로 이미 올라간 파일을 고칠 수 없고, 결국 매번 새 번호 파일을 **생성**해 커밋해야 한다. (2) 프로덕션 배포가 수동이라 생성물과 실제 적용분이 어긋나면 드리프트를 눈으로 찾아야 한다. (3) 기존 45벌의 사본을 정본으로 발라내는 이주가 선행된다. 얻는 것(국소성)보다 배포 경로에 지는 위험이 커서 기각.
- **Supabase 선언적 스키마(`supabase/schemas/` + `db diff`)**: 공식 기능이지만 `config.toml`과 로컬 CLI를 전제한다. 이 저장소는 일부러 `config.toml`을 두지 않고 각자 `supabase init` 하도록 안내한다([README](../../README.md)). 전제를 뒤집는 비용이 커서 기각.

## Consequences

- 규칙을 바꿀 때 함수 전문을 다시 붙여넣게 된다. **옮겨 적을 때 빠뜨리지 않았는지는 사람이 확인해야 한다** — 이 결정이 감수하기로 한 비용이다.
- 테스트는 마이그레이션 번호를 박아두면 안 된다. 죽은 사본을 검사하며 조용히 통과하기 때문이다(실제로 랭킹전 전투 테스트가 0082가 살아있는데 0080의 "반격" 로직을 단언하며 통과하고 있었다 — 0082는 반격 개념을 없앤 뒤였다). 함수 본문을 단언할 때는 [tests/migration-sql.ts](../../tests/migration-sql.ts)의 `latestFunction(name)`으로 **살아있는 정의**를 집는다.
- 특정 마이그레이션이 무엇을 **도입했는지**(테이블·제약·grant)를 단언하는 것은 그대로 파일을 읽어도 된다. 그건 영원히 참인 과거 사실이라 낡지 않는다.
