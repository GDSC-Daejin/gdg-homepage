# 동아리 운영을 위한 Linear 활용 메모

> 조사일: 2026-08-04 · 근거: Linear 공식 문서

## 추천 운영 단위

| 동아리 업무 | Linear 단위 | 최소 운영법 |
| --- | --- | --- |
| 운영진·개발·디자인의 해야 할 일 | Issue | 일 하나당 이슈 하나, 담당자·마감일·상태만 둔다. 이슈는 한 팀에 속하며 담당자, 프로젝트, 사이클, 라벨, 우선순위를 가질 수 있다. [공식 문서](https://linear.app/docs/conceptual-model) |
| 해커톤·행사·서비스 배포 | Project | 명확한 결과물/완료일이 있는 큰 일을 프로젝트로 묶고, 이슈·문서·마일스톤을 연결한다. 여러 팀이 함께 쓸 수 있다. [공식 문서](https://linear.app/docs/projects) |
| 2주 단위 운영 스프린트 | Cycle | 1–8주 반복 주기로 할 일을 담고, 미완료 이슈는 다음 사이클로 자동 이월된다. 시작 전에는 최근 3개 사이클 기준의 완료 가능성 추정도 보인다. [공식 문서](https://linear.app/docs/use-cycles) |
| 진행 현황 공유 | Project update | 프로젝트 리드가 매주 `On track / At risk / Off track`과 다음 행동을 작성하고, 필요하면 Slack 채널로 보낸다. 리마인더도 설정 가능하다. [공식 문서](https://linear.app/docs/initiative-and-project-updates) |

## 바로 만들 구성

1. 팀은 우선 `운영`, `프로덕트` 두 개만 둔다. 스터디별 팀 분리는 실제로 독립적인 백로그와 상태 흐름이 생길 때만 한다.
2. 공통 상태는 `Backlog → Todo → In Progress → Done`으로 시작한다. 워크플로는 팀별로 정의된 순서 있는 상태 집합이다. [공식 문서](https://linear.app/docs/conceptual-model)
3. 이슈 템플릿 3개만 만든다: `행사 준비`, `콘텐츠/홍보 요청`, `버그·개선 제안`. 폼 템플릿은 필수 입력값을 강제할 수 있고, Slack에서도 호출할 수 있다. [공식 문서](https://linear.app/docs/issue-templates)
4. 반복 행사는 프로젝트 템플릿으로 만든다. 템플릿에는 미리 정한 이슈·마일스톤·리드·멤버를 넣을 수 있다. [공식 문서](https://linear.app/docs/project-templates)
5. 공유 뷰는 `이번 주 내 일`, `담당자 없음`, `행사별 진행 중`, `마감 지연`만 저장한다. 필터한 이슈/프로젝트 뷰는 저장·공유·즐겨찾기할 수 있고, 보드/리스트와 그룹 기준을 바꿀 수 있다. [Custom Views](https://linear.app/docs/custom-views) · [Display options](https://linear.app/docs/display-options)

## 운영 리듬

- 월요일: 운영진이 다음 2주 Cycle에 이번 주에 끝낼 이슈만 넣고 담당자를 정한다.
- 주중: 각 담당자는 상태만 갱신한다. 막힌 일은 이슈 관계로 연결하거나 댓글에 도움을 요청한다.
- 금요일: 프로젝트 리드가 3문장 업데이트(상태·이번 주 결과·다음 주/위험)를 남긴다.
- 회고: Cycle 그래프로 범위와 완료 추이를 보고, 다음 사이클에는 할 일을 줄이는 쪽부터 검토한다. 그래프는 사이클 시작 뒤 자동 생성되고 변경에 맞춰 갱신된다. [공식 문서](https://linear.app/docs/cycle-graph)

## 도입 시 피할 것

- 모든 스터디·소모임을 처음부터 팀으로 만들지 않는다. 팀은 독립 워크플로가 필요할 때만 추가한다.
- 개인 할 일, 회의록, 공지까지 전부 이슈화하지 않는다. 결과물·담당·기한이 필요한 일만 이슈로 둔다.
- Cycle은 최소 한 번의 행사/개발 흐름이 안정된 뒤 켠다. 정기 리듬이 없으면 저장 뷰와 프로젝트만으로 충분하다.
