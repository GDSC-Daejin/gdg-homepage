# GDG DJU 서비스 위키 (디자이너 · LLM 공용)

> **이 문서는 뭔가요?**
> 디자이너가 쓰는 LLM 위키에 넣는 종합 정리본이에요. 사람(디자이너)이 읽어도 쉽고, LLM(클로드)이 읽고 디자이너 질문에 답할 수 있도록 **이 문서 하나로 맥락이 다 되도록** 자체 완결로 썼어요.
>
> **LLM에게**: 이 서비스에 대한 디자인/UX 질문을 받으면 이 문서를 기준으로 답하세요. 여기 "지금 이렇다(현황)"와 "이렇게 바꾸는 중이다(방향)"가 나뉘어 있으니 섞지 마세요. 확정 안 된 건 "논의 중"이라고 표시돼 있어요.

---

## 1. 이 서비스가 뭐예요

**GDG on Campus 대진대학교** 동아리를 위한 웹앱이에요.
신입을 뽑고 → 회원이 이벤트에 참여하고 → 운영진이 뒤에서 관리하는 것까지 한 곳에서 해요.

- 만든 것: Next.js + Supabase(로그인·데이터 저장) + Tailwind(디자인)
- 로그인: 구글 계정
- 알림: 이벤트·출석 관련은 Slack과 이메일로 자동 발송
- "둘러보기 모드": 로그인 안 해도 예시 데이터로 화면을 구경할 수 있는 기능

---

## 2. 세 종류의 사람

로그인 여부와 역할에 따라 **보이는 화면이 완전히 달라져요.**

| 누구 | 어떤 사람 | 뭘 하나 |
|---|---|---|
| 👀 **처음 온 사람** | 아직 회원 아님 (비로그인) | 구경하고 → 지원함 |
| 🙋 **회원** | 지원 합격해서 들어온 사람 | 이벤트 참여, 활동 |
| 🛠 **운영진** | 동아리를 굴리는 스태프 | 관리 전반 |

> 참고: 시스템 안에는 역할이 4개(지원자·회원·팀멤버·오거나이저)로 나뉘어 있지만, **실제로 화면이 갈리는 건 "회원"과 "운영진" 두 단계뿐**이에요. 그래서 디자인 상으로는 위 세 종류(비로그인 포함)만 신경 쓰면 돼요.

## 3. 지금 화면 구성 (현황)

### 처음 온 사람 (로그인 전) — 홍보용 화면

- **첫 화면(랜딩)** — 3D 오브, "배우고, 만들고, 배포한다" 문구, 활동 소개
- **소개 / 운영진 / 프로젝트** — 동아리 소개 페이지
- **지원하기** — 로그인 없이 바로 지원서 작성
- **면접 예약** — 합격 후보에게만 링크로 열림

### 회원 (로그인 후) — 메뉴 **11개**

| 메뉴 | 뭐 하는 곳 |
|---|---|
| 홈 | 다가오는 이벤트·안 한 설문·새 공지·이번 달 포인트 요약 |
| 이벤트 | 목록 → 신청 → 당일 출석 체크 |
| 공지 | 운영진 공지 읽기 |
| 회의록 | 모임 기록 (노션 연동) |
| 자유게시판 | 자유 글 |
| 질문답변 | 질문 올리고 답변 채택 |
| 설문 | 설문 응답 |
| 문의 | 운영진에게 문의 |
| 자료실 | 학습 자료 (노션 연동) |
| 프로필 | 내 정보·영어 닉네임·포인트·뱃지 |
| 출석이력 | 내가 출석한 기록 |

### 운영진 — 관리 화면 메뉴 **16개**

- **메인**: 대시보드
- **운영**: 회원 · 스터디/프로젝트 · 이벤트 · 장소 · 출석
- **모집**: 지원서 심사 · 면접 일정 · 면접 질문 · 모집 설정
- **콘텐츠**: 공지 · 설문 · 문의 · 자료실
- **관리**: 포인트/뱃지 지급 · 예산

### 핵심 흐름 3개

- **지원**: 첫 화면 → 지원하기 → (제출) → 결과는 이메일로
- **회원 참여**: 이벤트 신청 → 정원 넘치면 대기 → 당일 코드 입력해서 출석 → 포인트/뱃지 쌓임
- **운영진 심사**: 지원서 접수 → 심사(심사중/합격/불합격) → 합격 시 결과 메일 자동 발송

## 4. 지금 뭐가 문제인가 (피드백)

외부에서 세 가지 피드백이 들어왔어요.

1. 세 종류 손님을 한 앱이 동시에 담당해서 정신없다
2. 흐름이 복잡하고 단계가 깊다
3. 기능이 너무 많아 **"이 앱이 뭘 제일 잘하는지" 흐려졌다**

**세 개가 사실 한 뿌리예요:**

> "우리 앱이 제일 잘하는 한 가지"를 정하지 않아서, 이것저것 다 넣다 보니 메뉴가 불어났다.
> (회원 11 + 운영진 16 = 메뉴 **27개**. 동아리 앱치고 너무 많음)

그래서 순서는 **① 방향을 먼저 정한다 → ② 그 기준으로 메뉴를 정리한다** 예요.

---

## 5. 정할 방향 (논의 중, 제안 상태)

> ### 🎯 "멤버가 이벤트에 오고, 그게 쌓여서 또 오게 만드는 앱"
>
> **이벤트 발견 → 신청 → 출석 → 포인트/뱃지 → 또 온다**

이 흐름에 직접 도움 되는 게 주인공(이벤트·신청·출석·내 활동·지원), 나머지(게시판·자료실·설문 등)는 조연이에요.

⚠️ 이 방향은 **아직 확정 아님** — 팀 합의가 필요해요. (아래 §8 참고)

## 6. 바꾸려는 메뉴 구성 (계획)

### 회원 메뉴: 11개 → 5개

**지금**: 홈 · 이벤트 · 공지 · 회의록 · 자유게시판 · 질문답변 · 설문 · 문의 · 자료실 · 프로필 · 출석이력
**바꾸면**: **홈 · 이벤트 · 커뮤니티 · 자료실 · 프로필**

| 지금 | 어떻게 | 이유 |
|---|---|---|
| 자유게시판 · 질문답변 · 회의록 | → **커뮤니티** 하나로 (탭 구분) | 셋 다 "글 쓰고 읽는" 성격 |
| 공지 · 설문 · 문의 | → **홈 화면 안**으로 | 따로 찾기보다 홈에서 바로 보이는 게 눈에 잘 띔 |
| 출석이력 | → **프로필** 안 탭으로 | 내 기록이니까 |

> 중요: 아무것도 **삭제하지 않아요.** 묶거나 옮기는 거예요. 기능과 데이터는 그대로.

### 운영진 메뉴: 16개 → 6묶음

**바꾸면**: 대시보드 · 회원 · 이벤트 · 콘텐츠 · **모집** · 관리 (세부는 각 묶음 안 탭으로)

- **핵심은 "모집"**: 신입 뽑는 건 1년에 한두 번뿐인데 그 메뉴들이 1년 내내 자리를 차지 중. → **모집 기간에만 펼치고, 아닐 땐 접기.**

## 7. 지금 당장 고칠 버그

> 첫 화면(랜딩)에서 상단 **"이벤트"를 누르면 → 로그인 벽에 막혀서 → 다시 첫 화면으로 튕겨요.**
> 처음 온 사람에겐 막다른 길. **디자인보다 앞선 우선순위 1번.**

---

## 8. 아직 안 정해진 것 (팀 합의 필요)

- 앱의 "한 가지"를 **"이벤트 참여가 쌓이는 앱"** 으로 못 박을지
- 모집 메뉴를 **접어두기** vs **아주 단순한 별도 페이지로 빼기** 중 뭘로 할지
- 포인트/뱃지·예산·장소처럼 **작은 동아리에서 실제로 쓰는지 애매한 기능** — 실사용 데이터를 본 뒤 유지할지 줄일지 결정 (지금 지레짐작으로 없애지 않음)

---

## 9. 디자이너가 작업할 때 지켜야 할 선

LLM과 함께 디자인/재배치를 할 때 **이건 건드리지 않기:**

- **기능은 없애는 게 아니라 옮기거나 묶는 것** — "공지 메뉴 삭제"가 아니라 "공지를 홈으로 이동"
- **화면이 다루는 데이터·저장 방식은 그대로** (디자인만 바꾸고 뒤 로직은 유지)
- 메뉴를 재배치할 땐 **먼저 메뉴 목업으로 합의 → 그다음 구현** (바로 코드부터 X)

## 10. 쉬운 용어 사전

| 이 문서의 말 | 실제로 가리키는 것 |
|---|---|
| 처음 온 사람 | 로그인 안 한 방문자 (지원 전) |

| 모집 모드 | 신입 뽑는 기간에만 관련 메뉴를 펼치는 방식 |
| 둘러보기 모드 | 로그인 없이 예시 데이터로 화면 구경하는 기능 |
