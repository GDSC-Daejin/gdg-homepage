# GDG DJU 개발 하네스·루프 엔지니어링 핸드오프

> 목적: 다음 작업자가 이 저장소의 에이전트 개발 방식과 검증 루프를 빠르게 이어받기 위한 문서
>
> 작성 기준: 2026-09-07, `dev` 브랜치 `b74666c` 및 현재 워킹트리

## 0. 한 줄 요약

이 저장소는 별도의 `harness` 실행기를 두지 않고, `AGENTS.md`의 규칙, 계획서와 작업 프롬프트, 태스크별 검증, `.superpowers/sdd` 진행 원장·리포트, 경로 제한 커밋을 묶어 에이전트 작업을 통제한다. 루프는 `계획 읽기 → 좁은 범위 구현 → 가장 작은 검증 → 통합 검증 → 리뷰·기록 → 다음 태스크` 순서로 반복된다.

## 1. 용어를 이렇게 이해하면 된다

### 하네스

이 프로젝트에서 “하네스”는 코드 한 파일이나 명령 하나가 아니다. 에이전트가 작업 범위를 벗어나거나 검증 없이 완료했다고 보고하지 않도록 둘러싼 운영 장치의 묶음이다.

프로젝트 코드에 `harness`라는 공식 컴포넌트가 정의되어 있는 것은 아니다. 아래 파일과 관례를 하네스의 실제 구성으로 본다.

| 층 | 실제 구성 | 역할 |
| --- | --- | --- |
| 규칙 | `AGENTS.md`, `CLAUDE.md` | 언어, 범위, 검증, 커밋·푸시 제한을 고정한다. |
| 작업 입력 | `docs/plans/`, `docs/superpowers/plans/`, `docs/superpowers/specs/` | 목표, 영향 파일, 완료 조건을 태스크 단위로 쪼갠다. |
| 오케스트레이션 | `docs/plans/codex-implementation-prompts.md` | 서브에이전트 프롬프트, 병렬/순차 웨이브, 의존 순서를 정의한다. |
| 실행 경계 | 태스크별 파일 범위와 명시적 pathspec 커밋 | 다른 작업과 사용자 변경을 덮어쓰지 않게 한다. |
| 검증 | Vitest, TypeScript, Next build, 브라우저·배포 스모크 | 코드·타입·빌드·실행 환경을 단계별로 확인한다. |
| 상태 기록 | `.superpowers/sdd/progress.md`, `*-report.md` | 완료 커밋, 검증 결과, 우려사항, 사용자 후속 작업을 남긴다. |
| 안전장치 | `git status`, `git diff`, `git diff --check`, `git add <명시 경로>` | 공유 워킹트리에서 무관한 변경을 커밋하지 않게 한다. |

### 루프 엔지니어링

기능을 한 번에 크게 완성하려 하지 않고, 각 태스크를 작은 피드백 루프로 닫은 뒤 다음 태스크로 넘기는 방식이다. 이 저장소에서는 다음 순서가 반복된다.

```text
계획/브리프
  → 현재 상태·충돌 지점 확인
  → 최소 범위 구현
  → 실패를 확인하거나 좁은 검증 실행
  → 타입체크·테스트·빌드·브라우저 검증
  → diff/self-review
  → 태스크 리포트·진행 원장 기록
  → 범위 제한 커밋
  → 의존 태스크 통합 후 다음 루프
```

## 2. 실제 작업 루프

### 2.1 시작 전

1. `AGENTS.md`와 관련 계획서·스펙을 읽는다.
2. `git status --short`, 현재 diff, 최근 커밋을 확인한다. 현재 워킹트리는 사용자와 기존 작업의 미커밋 변경이 섞일 수 있으므로 기존 변경을 소유하지 않는다고 가정한다.
3. 수정할 함수의 모든 호출자와 기존 재사용 패턴을 먼저 찾는다. 새 유틸·추상화·의존성은 마지막 수단이다.
4. 계획서에 지정된 파일, 완료 조건, 검증 명령을 작업 계약으로 삼는다.

### 2.2 실행 중

- 작업은 가능한 한 하나의 기능·하나의 파일군으로 제한한다.
- 서로 다른 파일만 건드리는 작업은 병렬 웨이브로 묶을 수 있다.
- 공유 파일, 마이그레이션 번호, 네비게이션 같은 충돌 지점이 있으면 순차 웨이브로 돌린다.
- 기존 컴포넌트·스키마·헬퍼·테스트 패턴을 먼저 재사용한다.
- UI 작업은 데이터 흐름과 기존 경계를 유지하고, 테스트 하네스가 없는 부분에 저가치 클래스 문자열 테스트를 억지로 추가하지 않는다.

`codex-implementation-prompts.md`에는 이 원칙이 구체적으로 기록돼 있다. 예를 들어 그룹 A는 파일이 겹치지 않아 병렬 실행할 수 있지만, 그룹 B는 `types.ts`, `schemas.ts`, `AdminSidebarNav` 등의 공유 때문에 포인트 상점 → 재학 여부 → 회원 테이블 → 분석 대시보드 → 보안 순서로 처리한다.

### 2.3 검증 루프

태스크 성격에 따라 가장 작은 게이트부터 실행한다.

| 변경 유형 | 기본 게이트 | 이 저장소의 한계 |
| --- | --- | --- |
| 순수 함수·스키마 | 관련 Vitest 파일 → `pnpm exec tsc --noEmit` | 외부 서비스 호출은 mock으로 격리한다. |
| 마이그레이션·RPC | SQL 텍스트 계약 테스트, 필요하면 `latestFunction()`으로 최신 함수 정의 확인 | 라이브 DB 통합 테스트/pgTAP 인프라는 없다. |
| 서버 액션·페이지 | 타입체크 → 관련 테스트 → 필요 시 `pnpm test` | Supabase 실제 데이터와 권한은 별도 스모크가 필요하다. |
| UI·리디자인 | 타입체크·기존 테스트 유지 → preview 브라우저 확인 | 일반적인 RTL 컴포넌트 하네스와 자동 E2E가 중심이 아니다. |
| 통합 완료 | `pnpm test` → `pnpm build` | 외부 계정·시크릿·라이브 DB는 사용자 검증 영역이다. |

Vitest는 [`vitest.config.ts`](../vitest.config.ts)에서 `node` 환경으로 실행된다. `server-only`는 테스트용 별칭으로 치환되고, 마이그레이션 테스트는 파일을 읽어 정책과 최신 SQL 정의를 검증한다. `tests/migration-sql.ts`의 `latestFunction()`은 오래된 마이그레이션 사본을 검사해 테스트가 조용히 통과하는 문제를 막기 위한 대표적인 하네스 유틸이다.

현재 저장소의 알려진 기준선 실패는 `tests/accessibility-primitives.test.ts`가 설치되지 않은 eslint 의존성과 스크립트를 단언하는 문제다. 클린 트리에서도 재현되는 기존 실패이므로 `package.json`을 바꿔 해결하지 않는다. 검증 결과를 보고할 때는 신규 실패와 이 기준선 실패를 분리한다.

### 2.4 종료와 인계

태스크 종료 시 리포트에 최소한 아래 내용을 남긴다.

- 실제 수정·생성 파일
- 실행한 검증 명령과 결과
- 커밋 해시와 커밋에 포함된 정확한 경로
- 구현 중 발견한 우려사항과 사용자에게 남긴 라이브 확인
- 다음 태스크가 의존하는 파일·마이그레이션·환경변수

공유 워킹트리에서는 `git add -A`와 `git commit -a`를 사용하지 않는다. 명시 경로만 stage/commit하고, 커밋 전 `git show --stat HEAD`와 `git status --short`로 다른 작업이 섞이지 않았는지 확인한다. 푸시·PR·머지는 사용자의 승인 후 진행한다.

## 3. 이미 축적된 루프의 증거

- `.superpowers/sdd/progress.md`: MVP, Phase 2, 지도, IA 등 기능군별 태스크 상태, 커밋 범위, 통합 게이트, 후속 작업을 누적한다.
- `.superpowers/sdd/task-*-report.md`, `.superpowers/sdd/p2-task-*-report.md`: 구현자가 태스크별 변경 파일·검증·범위 준수·우려사항을 기록한다.
- Phase 2 기록은 P1~P9를 순서대로 통합하면서 `vitest 21/21 + build`를 최종 게이트로 확인했고, 중간 태스크에서 발견된 회귀를 다음 루프(P9)에서 고쳤다.
- 과거 작업 리포트에는 먼저 실패를 확인한 뒤 구현하고 다시 통과시키는 흐름, 동시 작업의 stage 오염을 diff로 발견해 분리한 흐름, 최종 whole-feature 리뷰 후 fix/re-review하는 흐름이 남아 있다.

즉, 이 프로젝트의 루프는 테스트 통과만을 목표로 하지 않는다. “작업 범위가 맞는가”, “현재 살아 있는 SQL을 검증하는가”, “다른 에이전트의 변경을 보존했는가”, “라이브 확인을 누가 해야 하는가”까지 함께 닫는 것이 완료 조건이다.

## 4. 다음 작업자가 바로 따를 체크리스트

### 시작

- [ ] `git status --short`로 기존 변경을 기록한다.
- [ ] `AGENTS.md`, 관련 plan/spec, `CONTEXT.md`를 읽는다.
- [ ] 현재 호출 흐름과 재사용 가능한 함수·컴포넌트·테스트를 찾는다.
- [ ] 공유 파일과 마이그레이션 번호 충돌을 확인한다.

### 구현

- [ ] 목표 파일과 완료 조건 밖으로 확장하지 않는다.
- [ ] 순수 로직은 작은 회귀 테스트를 남긴다.
- [ ] DB·외부 서비스·브라우저처럼 자동화되지 않은 경계는 수동 확인 항목으로 분리한다.

### 완료

- [ ] 관련 테스트와 타입체크를 실행한다.
- [ ] 필요한 경우 전체 `pnpm test`와 `pnpm build`를 실행한다.
- [ ] `git diff --check`와 파일 범위 self-review를 한다.
- [ ] 태스크 리포트와 진행 원장에 검증·커밋·잔여 작업을 기록한다.
- [ ] 명시 경로만 커밋하고, 푸시·PR·머지는 사용자에게 넘긴다.

## 5. 하네스가 아직 아닌 것

다음 항목은 현재 자동 하네스가 아니라 사람의 판단이나 수동 검증에 의존한다.

- 단일 명령으로 계획·에이전트·리뷰·커밋을 모두 관리하는 중앙 오케스트레이터는 없다.
- Vitest는 Node 환경이며, 전체 UI 상호작용을 덮는 RTL/E2E 하네스는 아니다.
- Supabase 실제 DB, RLS, 마이그레이션 적용 상태를 자동으로 검증하지 않는다.
- 외부 시크릿, Slack·Notion·Google·Vercel 연동, 로그인 후 브라우저 시나리오는 사용자 또는 배포 환경에서 확인한다.
- 현재 `.github/workflows`에는 `dev` 푸시 후 Slack 알림 워크플로만 확인되며, 테스트·빌드를 자동 실행하는 CI 워크플로는 이 저장소에서 확인되지 않는다.

따라서 새 기능을 이어받을 때 “테스트가 통과했다”와 “운영 경계까지 확인됐다”를 같은 말로 취급하지 않는다. 후자는 README 체크리스트, 계획서의 라이브 확인 항목, 사용자 승인 작업으로 별도 추적한다.
