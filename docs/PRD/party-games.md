# 동아리 파티게임 운영 페이지 기획안

## 1. 제품 정의

동아리 파티 이벤트에서 운영진 한 명이 게임 진행과 점수 집계를 관리하고, 결과를 대형스크린에 표시하는 현장 운영 도구다.

핵심 가치는 게임을 제공하는 것이 아니라 **여러 게임을 하나의 대회 흐름으로 묶어 진행 부담을 줄이는 것**이다.

### 대상 사용자

- 운영진: 파티 생성, 참가자 관리, 팀 배정, 라운드 점수 입력, 결과 표시
- 현장 참가자: 시스템에 접속하지 않고 대형스크린으로 팀·점수·순위 확인

### 제외 범위

- 닌텐도 스위치 게임, 카훗, 끄투, 구스구스덕 자체의 API/게임 화면 연동
- 실시간 음성·채팅
- 복잡한 개인별 업적·보상 시스템

## 2. 기본 사용자 흐름

1. 운영진이 파티 이벤트를 만든다.
2. 운영진이 실제 참석자 목록을 확인하거나 직접 입력한다.
3. 운영진이 팀 수를 정하고 랜덤 배정한다.
4. 필요하면 팀을 수동으로 바꾼 뒤 배정을 확정한다.
5. 운영진이 게임 라운드를 추가한다.
6. 각 라운드 종료 후 팀별 점수를 입력한다.
7. 운영진이 대형스크린에 상황판을 표시하고 현장 참가자가 함께 확인한다.
8. 마지막 라운드 종료 후 최종 순위와 결과를 공개한다.

## 3. MVP 범위

### A. 파티 개요

- 기존 `party` 이벤트와 연결
- 파티 상태: 준비 중 / 진행 중 / 종료
- 게임 목록: 마리오파티, 원투스위치, 51가지 세계게임 전집, 포커, 카훗, 끄투, 구스구스덕
- 사용자 지정 게임명 추가

### B. 참가자·팀

- 실제 참석자 목록 확인·추가·제외
- 팀 수 설정
- 랜덤 팀 배정
- 재추첨
- 운영진의 수동 팀 이동
- 팀 이름과 색상 설정
- 배정 확정 후 참가자에게 팀 표시

### C. 라운드·점수

- 게임 라운드 추가: 게임명, 라운드명, 점수 방식 메모
- 라운드별 팀 점수 입력·수정
- 라운드 완료/미완료 상태
- 누적 점수와 순위 자동 계산
- 동점 순위 표시

### D. 대형스크린 상황판

- 현재 진행 중인 게임
- 팀별 누적 점수·순위
- 최근 라운드 결과
- 전체 참가자 수·팀 수·완료 라운드 수
- 대형스크린 가독성 우선
- 운영진이 같은 화면에서 다음 라운드와 점수 입력을 조작

## 4. 운영진 화면과 대형스크린 표시

### 운영진 화면

- 파티 설정
- 참가자 및 팀 편집
- 라운드 추가·순서 변경
- 점수 입력
- 진행 상태 변경
- 최종 결과 공개

### 현장 표시 화면

- 별도 참가자 화면이나 참가자용 로그인 없음
- 운영진 화면에서 상황판을 표시
- 전체 팀 순위, 라운드 결과, 현재 게임, 다음 게임, 최종 결과를 대형스크린에 표시

참가자는 시스템 사용자가 아니다. 현장에서는 운영진 한 명이 모든 조작과 조회를 담당한다.

## 5. 우선순위가 높은 아이디어

| 우선순위 | 아이디어 | 이유 | 먼저 검증할 가정 |
|---|---|---|---|
| 1 | 랜덤 팀 배정 + 수동 조정 | 파티 준비에서 가장 반복적이고 실수 많은 작업 | 참가자 목록이 이벤트 신청자와 같으면 충분한가 |
| 2 | 라운드별 점수 입력과 누적 순위 | 페이지가 존재해야 하는 핵심 이유 | 운영진 1명이 현장에서 빠르게 입력할 수 있는가 |
| 3 | 대형스크린 상황판 | 모든 참가자가 현재 상황을 함께 이해 | 한 화면에 점수와 진행 상태를 함께 표시할 수 있는가 |
| 4 | 게임 템플릿과 사용자 지정 게임 | 게임 종류가 바뀌어도 재사용 가능 | 고정 목록만으로 첫 파티를 운영할 수 있는가 |
| 5 | 최종 결과 공개 | 파티의 종료감과 기록 제공 | 결과 화면을 별도 공유할 필요가 있는가 |

## 6. 데이터 개념

최소 개념은 다음 5개면 충분하다.

- `party`: 기존 이벤트와 연결된 파티 운영 단위
- `party_participant`: 파티 참가자
- `party_team`: 팀 이름·색상·순서
- `party_round`: 게임명·라운드명·진행 상태·순서
- `party_score`: 특정 라운드의 특정 팀 점수

팀 배정은 참가자와 팀의 관계로 저장하고, 점수는 팀 단위로 저장한다. 개인별 점수는 실제 요구가 생길 때 추가한다.

## 7. 화면 구조 초안

- `/admin/events/[id]/party`: 운영진 파티 설정·운영·스크린 표시

첫 구현에서는 별도 대시보드 메뉴를 추가하지 않고 관리자 이벤트 상세에서 진입한다. 운영진이 해당 URL을 대형스크린에 띄워 직접 진행한다.

## 8. 기술·운영 판단

- 기존 Supabase와 회원 권한을 재사용한다.
- 점수 입력은 서버 액션 또는 기존 데이터 변경 패턴을 따른다.
- 실시간 구독과 참가자별 갱신은 필요 없다. 운영진이 점수를 저장하면 같은 화면의 상황판이 갱신된다.
- 점수 수정 이력은 MVP에서 별도 감사 로그로 만들지 않는다. 운영진 권한과 현재 값 표시만 둔다.

## 9. 다음 기획에서 결정할 것

1. 실제 참석자 목록을 어떤 방식으로 빠르게 입력할지
2. 팀 배정 기준을 팀 수 중심으로 할지, 팀당 인원 중심으로 할지
3. 운영 화면과 대형스크린 표시 화면을 분리할지
4. 점수 체계를 모든 게임에서 동일한 숫자 합산으로 할지, 게임별 배점을 둘지
5. 운영진이 노트북으로 조작할지, 대형스크린 터치 환경에서도 조작할지

## 10. 추천 MVP 결정

첫 파티는 다음으로 고정한다.

- 운영진이 실제 참석자 목록을 직접 확인·입력
- 운영진이 팀 수를 지정
- 팀당 인원은 가능한 균등하게 랜덤 배정
- 운영진만 점수 입력
- 모든 라운드는 숫자 점수 합산
- 운영진 화면을 대형스크린에 표시

이 범위면 한 번의 실제 파티에서 준비 시간, 입력 속도, 대형스크린 가독성을 검증할 수 있다.

## 11. 사용자 스토리와 완료 기준

### 운영진

- 운영진으로서 파티 이벤트를 열고 참가자 수를 확인할 수 있다.
- 운영진으로서 팀 수를 정하고 참가자를 균등하게 랜덤 배정할 수 있다.
- 운영진으로서 배정 결과를 확인한 뒤 특정 참가자를 다른 팀으로 이동할 수 있다.
- 운영진으로서 게임 라운드를 추가하고 순서를 바꿀 수 있다.
- 운영진으로서 라운드 종료 후 모든 팀의 점수를 한 화면에서 입력할 수 있다.
- 운영진으로서 저장된 점수를 수정할 수 있다.
- 운영진으로서 파티를 진행 중 또는 종료 상태로 바꿀 수 있다.

### 현장 참가자

- 현장 참가자로서 대형스크린에서 내 팀과 팀원을 확인할 수 있다.
- 현장 참가자로서 전체 팀의 누적 점수와 순위를 확인할 수 있다.
- 현장 참가자로서 라운드별 결과와 다음 게임을 확인할 수 있다.

### MVP 완료 기준

- 참가자 수가 홀수여도 팀별 인원이 1명 이상 차이 나도록 배정된다.
- 팀 배정 전에는 참가자에게 팀이 노출되지 않는다.
- 배정 확정 전까지 재추첨과 수동 이동이 가능하다.
- 점수 저장 후 누적 점수와 순위가 새로 계산된다.
- 점수가 없는 팀도 0점으로 표시된다.
- 동점 팀은 같은 순위를 표시한다.
- 참가자는 별도 점수 입력 UI에 접근하지 않는다.
- 종료된 파티의 점수는 기본적으로 수정할 수 없다.

## 12. 화면별 상세 설계

### 운영진 파티 운영 화면

상단에는 파티명, 상태, 참가자 수, 팀 수, 완료 라운드 수를 표시한다.

탭은 세 개만 둔다.

1. `팀 배정`: 참가자 목록, 팀별 인원, 랜덤 배정, 재추첨, 수동 이동, 배정 확정
2. `게임 진행`: 라운드 목록, 현재 라운드, 라운드 추가, 팀별 점수 입력, 저장
3. `결과`: 최종 순위, 라운드별 결과, 결과 공개 상태

### 대형스크린 표시 영역

위에서부터 다음 순서로 표시한다.

1. 현재 상태와 현재 게임
2. 전체 팀 순위
3. 최근 라운드 결과
4. 다음 게임 또는 종료 안내

팀별 점수와 순위는 대형스크린에서 멀리서도 읽을 수 있어야 한다. MVP에서는 별도 차트보다 큰 숫자와 명확한 순위의 가독성을 우선한다.

## 13. 상태 전이 규칙

```text
준비 중 → 진행 중 → 종료
```

- `준비 중`: 참석자·팀·라운드 설정 가능
- `진행 중`: 점수 입력 가능, 팀 배정은 수동 수정 가능
- `종료`: 결과 조회만 가능

팀 배정 확정과 파티 상태 변경은 별개로 둔다. 팀을 확정하지 않아도 라운드 초안은 만들 수 있지만, 점수 입력은 팀 배정 확정 후에만 가능하게 한다.

## 14. 점수 및 순위 규칙

- 점수는 정수만 허용한다.
- 음수 점수는 허용하지 않는다.
- 점수 미입력과 0점은 구분한다. 미입력 라운드는 완료되지 않은 것으로 본다.
- 누적 점수는 완료된 라운드의 점수 합계다.
- 순위는 누적 점수 내림차순이다.
- 동점은 같은 순위로 표시한다.
- 점수 저장은 라운드 단위로 한다. 일부 팀만 저장되는 상태는 만들지 않는다.

게임별 배점표는 MVP에서 두지 않는다. 운영진이 게임마다 원하는 점수를 직접 입력하는 편이 규칙 변경에 강하고 구현도 작다.

## 15. 운영 당일 사용 시나리오

### 시작 전 10분

1. 운영진이 실제 참석자를 확인하고 목록에 추가·제외한다.
2. 팀 수를 입력하고 랜덤 배정한다.
3. 대형스크린에서 팀 구성을 확인하고 필요한 참가자만 이동한다.
4. 배정을 확정하고 팀 배정 화면을 상황판으로 전환한다.
5. 예정된 게임 라운드를 미리 추가한다.

### 게임 진행 중

1. 현재 라운드를 활성화한다.
2. 게임이 끝나면 팀별 점수를 입력한다.
3. 저장 후 상황판에서 순위가 바뀐 것을 확인한다.
4. 다음 라운드를 활성화한다.

### 종료 시

1. 마지막 라운드 점수를 저장한다.
2. 최종 순위를 확인한다.
3. 파티를 종료 상태로 변경한다.
4. 대형스크린에 최종 결과를 표시한다.

## 16. 위험 가정과 검증 방법

| 영역 | 가정 | 위험도 | 검증 방법 |
|---|---|---:|---|
| 가치 | 운영진은 점수 집계보다 팀 배정에서 더 큰 불편을 느낀다 | 높음 | 실제 운영진에게 기존 진행 방식과 소요 시간 질문 |
| 가치 | 참가자는 별도 접속 없이 대형스크린 순위판만으로도 충분히 이해한다 | 중간 | 모의 파티에서 화면 이해 여부 관찰 |
| 사용성 | 운영진 1명이 대형스크린에서 팀 이동과 점수 입력을 처리할 수 있다 | 높음 | 실제 4팀·20~24명 시나리오 테스트 |
| 사용성 | 한 화면에서 조작 영역과 표시 영역을 함께 사용해도 혼란이 없다 | 높음 | 운영 모드·표시 모드 전환 테스트 |
| 실행 가능성 | 실제 참석자 목록을 현장에서 빠르게 입력할 수 있다 | 높음 | 32명 명단 입력 시간 측정 |
| 실행 가능성 | 팀 단위 점수만으로 모든 후보 게임을 운영할 수 있다 | 중간 | 포커·카훗·구스구스덕 점수 산정 예시 작성 |

첫 번째 검증은 개발보다 **운영진이 종이에 팀을 배정하고 점수를 집계하는 현재 방식**을 관찰하는 것이 우선이다. 실제 문제가 팀 배정이 아니라 게임 규칙 합의라면 페이지의 중심을 점수판이 아닌 게임 진행 보조로 바꿔야 한다.

## 17. 다음 단계

다음 문서화 단계에서는 아래 순서로 진행한다.

1. 실제 파티 1회의 참가자 수와 팀 수를 정한다.
2. 운영 모드와 대형스크린 표시 모드를 한 화면으로 합칠지 분리할지 정한다.
3. 운영진용 팀 배정 화면 와이어프레임을 확정한다.
4. 점수 입력 화면의 한 라운드 시나리오를 확정한다.
5. Supabase 테이블과 관리자 권한 경계를 설계한다.
6. 그 후 MVP 구현 계획을 작성한다.

## 18. 인원 규모별 운영 원칙

인원이 늘어날수록 모든 게임을 전원이 동시에 하는 방식은 비효율적이다. 따라서 다음 두 개념을 분리한다.

- `대회 팀`: 행사 시작부터 끝까지 유지되는 점수 집계 단위
- `게임 유닛`: 특정 게임에서 실제로 함께 플레이하는 사람들의 단위

게임 유닛은 라운드마다 달라도 되지만, 결과 점수는 대회 팀으로 환산한다. 이 구조를 사용하면 40명이 되어도 팀 순위는 유지하면서 4~8명 단위 게임을 운영할 수 있다.

### 현재 고정할 배정 원칙

| 기준 | 정책 |
|---|---|
| 팀 수 | 최대 4팀 |
| 팀 규모 | 팀당 5~6명을 목표로 함 |
| 인원 차이 | 팀 간 인원 차이는 최대 1명 |
| 운영 기준 | 팀 수보다 팀원 간 대화와 친밀도를 우선 |

10~20명 규모에서는 위 원칙만으로 운영한다. 20명을 크게 넘는 경우의 팀 구조는 실제 인원과 행사 운영 방식을 확인한 뒤 별도로 결정한다.

## 19. 규모별 팀 게임 플랜

### 10명 안팎

- 2팀을 기본 후보로 둔다.
- 팀당 5명 안팎으로 구성한다.
- 카훗·끄투처럼 전원 참여가 가능한 게임은 전체 참가
- 마리오파티·원투스위치·포커는 2~4명씩 번갈아 출전
- 개인전 결과는 팀별 합산
- 라운드 수를 적게 하고, 팀 대항전의 긴장감을 중심으로 운영

추천 흐름:

1. 전원 참여 게임 1회
2. 2~4명 대표 게임 2~3회
3. 포커 또는 51가지 게임 전집 테이블 게임 1~2회
4. 최종 전원 참여 게임 1회

### 20명 안팎

- 4팀을 기본 후보로 둔다.
- 팀당 5~6명으로 구성한다.
- 매치업은 매 라운드 2팀씩 붙인다.
- 한 라운드에 2개의 게임 공간을 병렬로 운영할 수 있다.
- 같은 팀이 같은 시간에 여러 장소로 흩어지지 않도록 한 팀 단위로 출전자를 정한다.
- 모든 팀이 최소 한 번씩 서로 다른 상대를 만나도록 대진을 구성한다.

추천 대진 예시:

```text
1라운드: A-B / C-D
2라운드: A-C / B-D
3라운드: A-D / B-C
```

### 30명 이상

팀당 7명 이상이 되는 규모는 현재 기획에서 확정하지 않는다. 40명대에 도달하면 5명 단위 친목팀을 2개씩 묶어 4개 점수팀으로 운영하는 방안을 우선 검토한다.

## 20. 게임 유형별 운용 정책

| 게임 유형 | 예시 | 운영 방식 | 점수 환산 |
|---|---|---|---|
| 전체 참여형 | 카훗, 끄투, 구스구스덕 | 전원이 함께 플레이하거나 전체 방 사용 | 개인 결과를 팀별 합산 |
| 소규모 대항형 | 마리오파티, 원투스위치 | 팀에서 대표자를 선발해 2~4명 단위로 진행 | 경기 결과를 해당 팀 점수로 입력 |
| 테이블 순환형 | 포커, 51가지 세계게임 전집 | 여러 테이블을 만들고 참가자를 순환 | 테이블별 순위 또는 승패를 팀 점수로 변환 |
| 결승형 | 운영진이 선택한 대표 게임 | 상위 팀 또는 전체 팀 참가 | 높은 배점으로 마지막 역전 기회 제공 |

게임을 추가할 때는 이름만 등록하지 않고 다음 운영 정보를 함께 정한다.

- 참여 규모: 전체 / 팀 대표 / 테이블
- 한 게임의 최대 동시 인원
- 팀별 출전 인원
- 대기 팀의 처리 방식
- 승패를 팀 점수로 바꾸는 방법

## 21. 팀 배정 정책

### 기본 규칙

- 무작위 배정을 기본으로 한다.
- 팀 수는 최대 4개로 한다.
- 팀당 5~6명을 목표로 한다.
- 팀별 인원 차이는 최대 1명으로 한다.
- 팀 배정 확정 후 첫 게임 시작 전까지만 수동 이동을 허용한다.
- 첫 점수 입력 이후에는 팀을 변경하지 않는다.
- 불참자는 팀 재편성 없이 `불참`으로 표시한다.
- 팀원이 늦게 오면 기존 팀의 대체 인원으로 합류시킨다.

### 선택적 공정성 보정

실력·경험 차이가 큰 게임이 포함될 때만 운영진이 참가자에게 간단한 수준 태그를 붙일 수 있다.

- 초보 / 보통 / 숙련
- 게임 경험 없음 / 경험 있음

보정은 완전한 자동 최적화가 아니라, 랜덤 배정 후 특정 팀에 숙련자가 몰렸을 때 한두 명을 교환하는 정도로 제한한다. 첫 버전에서는 수준 태그 없이 완전 랜덤으로 시작한다.

## 22. 대규모 운영을 위해 추가할 데이터

기존 라운드 정보에 다음 선택 필드를 추가하면 규모별 운영을 표현할 수 있다.

- `participation_mode`: 전체전 / 대항전 / 스테이션 / 테이블
- `unit_size`: 게임 유닛의 권장 인원
- `station_count`: 동시에 운영할 게임 공간 수
- `rotation_order`: 팀별 참여 순서
- `score_rule_note`: 팀 점수 환산 메모

참가자별 실제 출전 기록은 첫 버전에서 필수 데이터로 만들지 않는다. 운영진이 화면에서 확인해야 할 때만 추가한다. 처음부터 출전 로테이션을 자동 최적화하면 운영 도구보다 복잡한 배정 시스템이 된다.
