# 지원서

## 페이지 기본 정보
| 항목 | 내용 |
|---|---|
| 라우트 | /apply |
| 접근 권한 | 회원 (role=applicant 전용 실질 기능, 그 외 role은 안내만) |
| 한 줄 목적 | 지원자가 이번 시즌 지원서를 작성하거나 자신의 지원 상태를 확인한다 |
| 대상 사용자 | 아직 정회원으로 전환되지 않은 지원자(applicant) |

## 페이지 목적 · 사용자 목표
- 지원서를 한 번 작성해 제출한다 (시즌당 1회)
- 제출 후에는 심사 상태(심사 중/합격/불합격)를 확인한다

## 정보 구조 (Information Architecture)
1. 헤더: "지원서" + 현재 시즌명 설명
2. 카드 1개 내부에 조건 분기
   - 이미 지원한 경우: 상태 뱃지 표시
   - 아직 지원 전인 경우: 지원서 작성 폼
   - role이 applicant가 아닌 경우(이미 회원): 안내 문구만

## 주요 UI 요소 · 표시 데이터
- 지원서 폼: 질문 3개(자기소개, 지원 동기, 관심 분야) — 각각 필수 입력 textarea
- 상태 뷰: "지원 상태" 라벨 + 뱃지(심사 중=warning, 합격=success, 불합격=danger)
- CURRENT_SEASON 값을 부제목에 노출

## 상태 (States)
- role이 admin/member(이미 회원): "이미 회원입니다" 안내 카드만 표시, 폼 없음
- 미지원 상태: 빈 폼 표시
- 지원 완료 상태: 폼 대신 상태 뱃지만 표시 (재작성/수정 불가)
- 제출 중: 버튼 비활성화
- 제출 실패: 폼 하단에 에러 텍스트(빨간색) — 예: "모든 항목을 입력해주세요", "이번 시즌에 이미 지원했어요"

## 인터랙션 · 액션
- 폼 제출 → 성공 시 페이지가 상태 뷰로 전환(재조회), 실패 시 인라인 에러만 표시
- 제출은 시즌당 1회로 제한되어 있어 중복 제출 시도는 서버에서 에러로 막힘

## 디자인 의도 · 강조점
- 지원 전/후 화면이 완전히 다른 모드이므로, 전환 시점(제출 성공)의 피드백이 명확해야 함
- 세 질문은 순서(자기소개→동기→관심분야)대로 자연스러운 서술 흐름을 유도하는 구성
- 심사 상태는 뱃지 하나로 결과를 즉시 인지할 수 있게 — 색상 대비 확실히

## 반응형 · 접근성 노트
- 폼 전체 폭 카드 안에 배치, 모바일에서도 textarea 4행 유지로 입력 편의 확보
- 에러 메시지는 텍스트로 제공(색상만으로 구분하지 않음)
