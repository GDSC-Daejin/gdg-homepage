# 공지 수정 (어드민)

## 페이지 기본 정보
| 항목 | 내용 |
|---|---|
| 라우트 | /admin/notices/[id] |
| 접근 권한 | 어드민 |
| 한 줄 목적 | 기존 공지의 내용을 수정하거나 발행/삭제한다 |
| 대상 사용자 | 공지를 관리하는 운영진 |

## 페이지 목적 · 사용자 목표
- 이미 작성된 공지의 제목/본문을 수정한다
- 미발행 공지를 발행 상태로 전환한다 (발행 시 알림 채널로 공지가 전달됨)
- 더 이상 필요 없는 공지를 삭제한다

## 정보 구조 (Information Architecture)
1. 페이지 헤더("공지 수정") + 우측 액션 영역(발행 버튼, 삭제 버튼)
2. 단일 카드 안에 수정 폼 (작성 화면과 동일한 폼, 기존 값이 채워진 상태)

## 주요 UI 요소 · 표시 데이터
- 헤더 우측: 발행 버튼(이미 발행된 공지는 버튼 자체가 숨겨짐), 삭제 버튼
- 폼: 제목(기존 값), 본문(기존 값), "수정" 버튼

## 상태 (States)
- 존재하지 않는 공지 id: 404 처리
- 이미 발행된 공지: 발행 버튼 미노출 (재발행 불가)
- 발행 처리 중 / 삭제 처리 중: 버튼 비활성화
- 발행 성공: 발행 관련 안내 메시지(연동 알림 발송 결과) 인라인 표시, 화면 새로고침으로 발행 버튼 사라짐
- 발행/삭제 실패: 각 버튼 옆 인라인 에러
- 수정 폼 제출 성공: 페이지 새로고침(같은 화면 유지, 최신값 반영)
- 수정 폼 제출 실패: 폼 하단 인라인 에러

## 인터랙션 · 액션
- 발행 버튼 클릭 → 즉시 발행 처리(별도 확인창 없음) → 발행 후에는 되돌릴 수 없는 일회성 액션이며, 발행 시 연동 알림(예: 슬랙)이 발송될 수 있고 그 결과 메시지가 노출됨
- 삭제 버튼 클릭 → confirm("삭제할까요? 되돌릴 수 없어요") → 확인 시 삭제 후 목록으로 이동
- 수정 폼 제출 → 저장 후 같은 화면 유지(리스트로 이동하지 않음)

## 디자인 의도 · 강조점
- 발행은 되돌릴 수 없는 중요한 액션이므로 삭제와 함께 헤더에 나란히 있어도 시각적 위계(강조 vs 위험)를 구분해야 함
- 발행 후 알림 발송 결과 메시지는 운영진에게 "정말 나갔는지" 확인시켜주는 안심 장치이므로 놓치지 않게 배치
- 폼 자체는 작성 화면과 동일한 톤 유지, 다만 이미 존재하는 공지를 다루는 느낌을 헤더의 액션 버튼들로 전달

## 반응형 · 접근성 노트
- 좁은 화면에서 헤더의 발행/삭제 버튼이 줄바꿈되어도 탭 영역이 좁아지지 않게
- 발행 여부에 따른 버튼 노출/숨김은 스크린리더 사용자에게도 상태가 명확히 전달되어야 함
- 삭제 확인은 브라우저 기본 confirm에 의존 중 — 디자인 시스템 톤에 맞는 확인 모달로 대체 고려 가능
