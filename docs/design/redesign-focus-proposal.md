# 방향성·복잡도 개선안 (피드백 대응)

> 2026-07 외부 피드백 3건에 대한 진단과 개선 기획. 근거는 현행 코드/라우트 실측(2026-07 기준). 이 문서는 **기획·개선안**이며 구현 코드는 포함하지 않는다. AGENTS.md의 UI 재설계 워크플로(레퍼런스 합의 → 기능·데이터 계약 보존)를 따른다.

## 들어온 피드백

1. 외부인 / 일반 멤버 / 운영진 **3개 타겟을 한 앱이 동시**에 담당 → 도메인 분리 필요성 건의
2. 유저 플로우가 **너무 복잡하고 depth가 깊다** → depth 감소, 기능 압축·통합 건의
3. 기능이 너무 많아 **이 서비스가 뭘 해결하는지 모호** → 방향성 정리 건의

---

## 1. 진단: 세 피드백은 한 뿌리다

셋은 별개 문제가 아니라 **하나의 원인이 세 증상으로 나타난 것**이다.

> **코어 잡(job-to-be-done)을 선언하지 않은 채 "동아리 운영에 필요할 법한" 기능을 계속 증축 → 도메인 엔티티 ~23개 / 마이그레이션 34개로 비대화 → 그 무게를 감당하려 멤버 11 + 운영진 16 = 내비 27개의 깊은 다중역할 IA가 생김.**

실측 근거:

- **엔티티 ~23개**(sponsors 제거 후 실존 27 테이블 중 인프라성 4 제외). init 이후 phase2·recruiting·interview·groups·meetings·notifications가 계속 얹혔다.
- **내비 27개**: 멤버(홈/이벤트/공지/회의록/자유게시판/질문답변/설문/문의/자료실/프로필/출석이력) + 어드민(대시보드/회원/스터디·프로젝트/이벤트/장소/출석/지원서/면접일정/면접질문/설정/공지/설문/문의/자료실/포인트/예산).
- **모집 파이프라인이 4개 라우트로 분산**: `admin/applications` · `interviews` · `interview-questions` · `settings`.
- **member/admin 이중 존재**: events·notices·surveys·inquiries·materials·attend. 그중 **자료실은 코드까지 복붙**(`(member)/materials`와 `admin/materials`가 거의 동일, admin판에 관리 기능 없음).

즉 피드백 #1·#2는 #3의 결과다. **먼저 방향성(#3)을 정하면 무엇을 통합·제거할지(#2)와 타겟을 어떻게 나눌지(#1)가 자동으로 따라온다.**

## 2. 각 피드백에 대한 입장

### #1 "3 타겟 → 도메인 분리" — 부분 동의, 단 **literal 도메인 분리는 반대**

**타겟 경계는 이미 코드에 존재한다.** 비로그인 `/`→`Landing`, 로그인→`MemberShell`, 운영진→`/admin` 별도 shell. 고통의 원인은 *호스팅·앱을 공유해서*가 아니라 그 위에 쌓인 기능 과잉이다.

별도 도메인/앱으로 물리 분리하면 무료 플랜 소규모 동아리에서 **인증 세션·Supabase·배포·유지보수가 2~3배로 쪼개진다.** DB는 어차피 하나라 얻는 게 적고 잃는 게 크다. → **물리 분리 대신 이미 있는 seam(공개/멤버/운영)을 선명하게 다듬는다.**

단, 하나는 진짜 분리가 맞다: **모집(ATS)은 시즌성 별도 잡**이다. 지원서·면접·면접질문·모집설정은 1년에 한두 번만 쓰는데 평소 운영진 내비를 항상 차지한다. → 도메인이 아니라 **"모집 모드"로 접어두기**(모집 기간에만 펼쳐지는 단일 섹션).

또한 **4-role인데 실효 게이팅은 멤버/운영진 2단계뿐**이다(organizer·team_member가 `/admin` 전 구역 동일 접근). role 세분화가 접근제어 가치를 못 낸다 — 이 사실이 "타겟이 많아 보이는데 실제 경계는 단순"함을 뒷받침한다.

### #2 "복잡·depth 깊음 → 압축·통합" — 전적으로 동의

가장 실행 가치가 높다. 데이터 계약을 건드리지 않고 IA만 접어도 체감이 크게 는다. 구체안은 §3-C, §3-D.

### #3 "기능 과다 → 방향성 모호" — 동의, 그리고 **가장 먼저 풀어야 함**

핵심은 기능을 무작정 자르는 게 아니라 **코어 잡을 선언하고 모든 기능을 그 기준으로 코어/보조/유예로 줄 세우는 것**이다. 랜딩 카피("배우고, 만들고, 배포한다", "참여")와 기존 `../plans/improvement-proposals.md`(자동 포인트·리마인더·홈 대시보드)가 이미 **참여 루프**를 가리키고 있다 — 방향 감각은 맞다. 명시적으로 못 박지 않았을 뿐.

## 3. 개선안

### A. 코어 잡 선언 (제안)

> **"멤버가 이벤트에 참여하고, 그 참여가 쌓여 다시 오게 만든다."**
> 참여 루프: **이벤트 발견 → 신청 → 출석 → 포인트/배지 → 리텐션**

- 이 루프에 **직접 기여**하면 코어. 지원(신규 유입)과 프로필(내 활동)은 루프의 입구/거울이라 코어에 붙는다.
- 나머지(게시판·자료·설문·문의·예산 등)는 **보조**. 있어도 되지만 내비 1급 시민일 필요는 없다.
- 멤버 홈(`HomeDashboard`)이 이 루프의 얼굴이 되게 한다. (이미 존재 — 강화만.)

### B. 도메인은 나누지 말고 seam 3개를 선명하게

| Seam | 대상 | 조치 |
|---|---|---|
| 공개 | 외부인 | 마케팅+지원 전용. 로그인 벽에 막히는 링크 제거(§3-D 데드엔드). |
| 멤버 앱 | member+ | 참여 루프 중심으로 내비 압축(§3-C). |
| 운영 | staff | 상시 운영 vs **시즌 모집 모드** 분리. |

물리 도메인 분리는 하지 않는다.

### C. IA 통합 — 내비 27 → ~11

**멤버 사이드바 11 → 5**

| 유지(코어) | 통합 | 접기 |
|---|---|---|
| 홈, 이벤트, 프로필 | **커뮤니티** ← 자유게시판+질문답변+회의록 (모두 posts 계열, 이미 `PostListPage` 공유) | 공지·설문·문의는 top-level 제거하고 **홈 대시보드의 피드/할 일 카드**로 노출 |
| 자료실 | | 출석이력 → 프로필 안 탭으로 |

→ 결과: **홈 · 이벤트 · 커뮤니티 · 자료실 · 프로필**. (공지/설문/문의는 사라지지 않고 홈에서 발견성이 오히려 상승)

**운영진 사이드바 16 → 6 (그룹=1급 진입점, 내부는 탭)**

| 그룹 | 내부 탭 |
|---|---|
| 대시보드 | (모집 기간엔 유입/심사 현황 위젯 노출) |
| 회원 | 회원 · 스터디·프로젝트 |
| 이벤트 | 이벤트 · 출석 · 장소 |
| 콘텐츠 | 공지 · 설문 · 문의 · 자료실 |
| **모집(시즌)** | 지원서 · 면접일정 · 면접질문 · 모집설정 — **모집 닫히면 접힘** |
| 관리 | 포인트 · 예산 · (감사) |

기존 `AdminSidebarNav`의 그룹 구조(운영/모집/콘텐츠/관리)가 이미 이 뼈대다. **그룹 제목을 실제 진입점으로 승격하고 하위를 탭으로 넣는 작업**이라 신규 설계가 아니라 재배치다.

### D. depth·중복 즉시 정리 (데이터 계약 무변경, 저위험)

1. **온보딩 리다이렉트 3연쇄 축소**: `auth/callback → auth/complete → onboarding → /`. `auth/complete`는 순수 리다이렉트 전용 페이지 — callback에서 바로 목적지로 보내 1홉 제거 검토. `student_no` 게이트가 auth.ts·root·onboarding **3곳 중복 검사** → 한 곳(미들웨어 or 공통 가드)로 수렴.
2. **자료실 중복 제거**: `admin/materials`가 member판 복붙에 관리 기능 없음 → admin 자료실은 멤버 자료실 재사용 + 편집 액션만 얹거나, 관리 필요 없으면 삭제.
3. **랜딩 데드엔드 수정**: `landing-preview/Landing.tsx`의 `/events` 링크는 공개 `/events`가 없어 비로그인 클릭 시 `/`로 튕김. → 공개용 이벤트 미리보기 라우트를 두거나 링크를 `/about#activities` 등 실존 앵커로 교체. **버그성 — 우선순위 상.**
4. member/admin 이중 이벤트/공지/설문: 데이터·권한이 다르니 라우트 분리는 유지하되, 멤버측을 §3-C대로 홈/커뮤니티로 흡수해 top-level 노출만 줄인다.

### E. 기능 keep / fold / defer 분류

| 분류 | 기능 | 근거 |
|---|---|---|
| **Keep(코어)** | 이벤트, 신청·대기열, 출석 체크인, 홈 대시보드, 프로필, 지원(공개) | 참여 루프 직접 구성 |
| **Fold(통합/흡수)** | 자유게시판·QnA·회의록→커뮤니티, 공지·설문·문의→홈 피드, 출석이력→프로필, 모집 4종→모집 모드 | 개념 중복·저빈도 |
| **Defer(검증 후 결정)** | 포인트/배지, 예산, 장소, 통합검색, 알림센터 | 소규모 동아리 저사용 추정 — `../plans/improvement-proposals.md`의 "사람 없이 확인" 쿼리로 실사용 데이터 본 뒤 판단 |

**주의**: Defer는 삭제가 아니다. `../plans/improvement-proposals.md`에 이미 정의된 검증 쿼리(포인트↔출석률 상관, 알림 발생 빈도 등)를 먼저 돌려 근거를 만든 뒤 유지/축소를 정한다.

## 4. 실행 순서 · 역할 경계

우선순위(저위험·고체감 우선):

1. **랜딩 데드엔드 수정**(§3-D-3) — 버그, 즉시.
2. **멤버 내비 압축 11→5**(§3-C) — 데이터 무변경, 체감 최대.
3. **운영진 그룹→탭 재배치 + 모집 모드**(§3-C, §2 시즌).
4. **온보딩 홉/중복 검사 정리**(§3-D-1), **자료실 중복 제거**(§3-D-2).
5. **Defer 기능 실사용 검증 쿼리 → 유지/축소 결정**(§3-E).

**역할 경계(프로젝트 관행)**: 이 문서까지가 기획 산출물이다. 실제 구현은 코어 잡 합의 후, 각 항목을 작은 PR 단위로 쪼개 진행하길 권한다. IA 재배치(2·3)는 레퍼런스(내비 목업)를 먼저 합의하고 착수 — 기능·데이터 계약은 보존한다.
