# Linear 이슈 템플릿

작업은 Linear `gdg-dju` 워크스페이스의 `GDG` 팀(https://linear.app/gdg-dju/team/GDG/overview)에서 이슈로 관리한다. 이 문서는 이슈 템플릿의 원본이다. Linear의 템플릿을 고치면 이 문서도 같이 고친다. PR 템플릿은 [.github/pull_request_template.md](../.github/pull_request_template.md)에 있다.

이슈는 작업 전에, PR은 작업 후에 쓴다. 그래서 이슈의 섹션은 PR 템플릿과 짝을 이룬다.

| 이슈 | PR | 차이 |
| --- | --- | --- |
| 배경 | 배경 | 같다 |
| 목표 | 의도 | 이슈는 끝났을 때 달라질 것을 체크리스트로 쓴다 |
| 범위 · 접근 방향 | 구현 | 이슈는 손대도 되는 곳을 정하고, PR은 실제로 바꾼 것을 쓴다 |
| 신중히 볼 점 | 중점 리뷰 사항 | 이슈에 적힌 위험은 PR에서 리뷰 대상으로 이어진다 |
| 확인 방법 | 확인 방법 | 같은 체크리스트를 PR에서 실행 결과로 채운다 |
| 기타 | 기타 | 같다 |

## 등록 방법

Linear에서 Settings → Teams → GDG → Templates → New template → Issue template을 열고 아래 세 템플릿을 하나씩 만든다. 템플릿마다 기본 라벨을 지정한다.

## 운영 규칙

- **라벨**: 영역(`프론트`·`백엔드`·`디자인`·`운영`)에서 하나, 유형(`기능`·`개선`·`버그`)에서 하나. 영역은 어느 하위 세션이 맡을지를 정한다.
- **상태**: Backlog(본문이 덜 채워짐) → Todo(하위 세션에 넘길 수 있음) → In Progress(하위 세션 작업 중) → In Review(오케스트레이터가 diff 리뷰·검증 중, 팀에 없으면 생략) → Done(dev에 합쳐짐).
- **모델**: "신중히 볼 점"이 채워져 있으면 Opus, "없음"이면 Sonnet으로 시작한다. 오케스트레이터가 최종 판단한다.
- **연결**: 브랜치 이름에 이슈 번호를 넣고(예: `gdg-12-store-tab`), PR 본문에 `Closes GDG-12`를 쓴다. 자동으로 Done이 되려면 Linear의 GitHub 연동이 켜져 있고 PR로 머지돼야 한다. 로컬에서 dev에 바로 합친 작업은 Done으로 직접 옮긴다.

---

## 1. 작업 (기능·개선·디자인)

기본 라벨: 유형 `기능`. 영역은 작성자가 고른다.

```markdown
## 배경

<!-- 왜 이 작업이 필요한지 써요. 요청한 사람과 관련 이슈·문서·슬랙 링크도 붙여요 -->

## 목표

<!-- 끝났을 때 무엇이 달라지는지 써요. 화면에서 눌러 보고 확인할 수 있게 써요 -->

- [ ]

## 범위

<!-- 작업하는 세션이 어디까지 손대도 되는지 정해요 -->

- 바꿀 곳:
- 손대지 않을 곳:
- 이번에 하지 않는 것:

## 접근 방향

<!-- 정해 둔 설계나 선택지가 있으면 써요. 없으면 "작업 세션이 판단" -->

## 신중히 볼 점

<!-- 권한·데이터 정합성·운영 영향·디자인 결정처럼 잘못되면 되돌리기 어려운 곳을 써요. 없으면 "없음" -->

## 확인 방법

- [ ] `pnpm exec tsc --noEmit`
- [ ] `pnpm test`
- [ ] `pnpm build`
- [ ] <!-- 화면 확인: 어느 주소에서 무엇을 눌렀을 때 무엇이 보여야 하는지 -->

## 기타

<!-- 참고 파일, 시안, 선행·후속 이슈를 써요. 없으면 "없음" -->

<!--
- 제목은 끝났을 때의 결과를 한 줄로 써요. 예: 프렌들리숍을 포켓몬 탭 안으로 옮긴다
- 라벨은 영역(프론트·백엔드·디자인·운영)에서 하나, 유형(기능·개선)에서 하나를 붙여요.
- 다른 이슈가 먼저 끝나야 하면 Linear의 Blocked by 관계로 연결해요.
- 브랜치 이름에 이슈 번호를 넣어요. 예: gdg-12-store-tab
- PR 본문에 Closes GDG-12를 쓰면 머지될 때 Done으로 옮겨져요. 연결만 하려면 Refs GDG-12로 써요.
-->
```

## 2. 버그

기본 라벨: 유형 `버그`.

```markdown
## 증상

<!-- 무엇이 잘못 보이거나 동작하는지 써요 -->

## 재현 방법

1. 주소:
2. 계정: <!-- 비로그인 · 회원 · 운영진 · 둘러보기 -->
3. 한 행동:
4. 실제 결과:

## 기대 동작

<!-- 원래 어떻게 돼야 하는지 써요 -->

## 근거

<!-- 스크린샷, 콘솔·서버 로그, 처음 발견한 날짜, 의심되는 커밋을 붙여요 -->

## 신중히 볼 점

<!-- 운영 데이터가 이미 잘못 쌓였는지, 다른 화면도 같은 원인일지 써요. 없으면 "없음" -->

## 확인 방법

- [ ] 재현 방법대로 했을 때 기대 동작이 나온다
- [ ] 같은 증상이 다시 생기지 않게 막는 테스트가 추가됐다
- [ ] `pnpm exec tsc --noEmit` · `pnpm test` · `pnpm build`

## 기타

<!-- 임시 우회 방법이나 후속 작업을 써요. 없으면 "없음" -->

<!--
- 제목은 증상을 한 줄로 써요. 예: 지원서 상세에서 예전 답변이 "-"로 보인다
- 라벨은 영역 하나와 유형(버그)을 붙여요. 운영 중인 사용자에게 영향이 있으면 우선순위를 High 이상으로 올려요.
- PR 본문에 Closes GDG-12를 쓰면 머지될 때 Done으로 옮겨져요.
-->
```

## 3. 운영 (DB 마이그레이션 · 환경변수 · 외부 서비스 · 배포)

기본 라벨: 영역 `운영`.

```markdown
## 배경

<!-- 어떤 작업 때문에 운영 반영이 필요한지 써요. 관련 이슈를 연결해요 -->

## 반영할 것

- [ ] <!-- 예: 마이그레이션 0123 적용, Vercel에 RESEND_WEBHOOK_SECRET 추가 -->

## 선행 조건

- 관련 코드: <!-- dev에 합쳐짐 · 푸시됨 · 배포됨 중 어디까지 왔는지 -->
- 먼저 끝나야 하는 이슈:

## 영향

<!-- 지금 운영 중인 코드와 맞는지, 데이터가 지워지거나 바뀌는지 써요 -->

## 실행 순서

1. 현재 상태 확인 <!-- 예: supabase migration list -->
2.
3. 반영 후 같은 명령으로 다시 확인

## 직접 해야 할 일

<!-- 대시보드 설정처럼 에이전트가 할 수 없는 일을 써요. 없으면 "없음" -->

## 되돌리는 방법

<!-- 문제가 생기면 어떻게 원래대로 돌리는지 써요 -->

<!--
- 제목은 반영할 내용을 한 줄로 써요. 예: 운영 DB에 마이그레이션 0123 적용
- 라벨은 영역(운영)을 붙여요. 운영 이슈는 사용자 승인 없이 실행하지 않아요.
-->
```
